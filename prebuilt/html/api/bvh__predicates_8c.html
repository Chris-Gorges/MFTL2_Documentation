    Detailed Description¶

    Author:

    Christian Gorges

    Date:

    2026-08-16

    Everything here is double precision. The broad phase may be loose (outward rounded float boxes); the narrow phase may not be wrong.

    Why only the orientation test is adaptive. It is the only predicate whose SIGN decides the answer: Guigue-Devillers branches on it up to eight times per pair (six plane classifications, two in check_min_max; the permutation cascade branches on signs already computed). A wrong sign sends the algorithm down a branch for a configuration that does not exist and typically reports a clean miss for two crossing triangles. Distances and interval endpoints degrade continuously and only move decisions sitting on the tolerance.

    The determinant is ill-conditioned exactly where this library works: thin films (four points coplanar to within the gap) and small features at large coordinates (the differences cancel the offset and its digits). Measured with examples/orient3d_predicate_profile.c (20 000 samples per row, adaptive form as the exact reference): the plain determinant misclassified 0 % at gap/L >= 1e-12, up to 0.035 % at 1e-14, 0.125 % at 1e-15 and 4.7 % at 1e-16. The adaptive form costs 3.66 ns against 1.83 ns in general position (40 ns only for exactly coplanar input), i.e. at most 6.2 % of a 176 ns MFTL_TriTriProximity() call. It is kept because the failure it removes is silent; MFTL_Orient3DFast() is the plain form.

    Shewchuk's construction (Discrete Comput. Geom. 18, 1997) is a filter: the plain determinant plus a comparison against a rigorous relative error bound, with exact expansion arithmetic only when the estimate cannot certify the sign.

    function MFTL_Orient3D¶

    Robust orientation predicate: six times the signed volume of the tetrahedron (pa, pb, pc, pd), with an EXACT sign (Shewchuk 1997). 

    double MFTL_Orient3D (
    const double pa,
    const double pb,
    const double pc,
    const double pd
)

    \(\[ \orient(\vect{a},\vect{b},\vect{c},\vect{d}) = (\vect{a}-\vect{d})\cdot\big[(\vect{b}-\vect{d})\times(\vect{c}-\vect{d})\big], \]\) positive when pd lies below the plane through pa, pb, pc, i.e. when those appear counter-clockwise seen from above. Adaptive: the plain determinant plus a comparison against a rigorous error bound; exact expansion arithmetic only when that bound cannot certify the sign.

    It is the one predicate whose SIGN decides an answer (Guigue-Devillers takes up to eight per pair); a wrong sign can report a clean miss for crossing triangles. Measured: 2.00x the plain determinant, at most 6.2 % of an MFTL_TriTriProximity() call; the plain form never misclassified in 20 000 samples at gaps >= 1e-12 of the body size and fails only at 1e-14..1e-16 (examples/orient3d_predicate_profile.c). Requires -ffp-contract=off.

    Parameters:

    • pa First point of the reference plane.
    • pb Second point.
    • pc Third point.
    • pd The point being classified.

    Returns:

    \(6V\); the SIGN is exact, the magnitude approximate.

    function MFTL_TriTriProximity¶

    Contact predicate: intersection, or a minimum distance within tolerance . 

    int MFTL_TriTriProximity (
    const double A,
    const double B,
    double tolerance
)

    MFTL_TriTriIntersect() first (a piercing pair has positive distance to every edge and vertex, so the distance test alone would miss it), then the exact minimum distance of two disjoint closed triangles: nine edge-edge and six point-face terms.

    Parameters:

    • A Corners of the first triangle.
    • B Corners of the second, in the same periodic image as A.
    • tolerance Gap at which contact is declared, >= 0.

    Returns:

    1 on contact, 0 otherwise.

    ** **

    176 ns/pair, against 31 ns for MFTL_TriTriIntersect() alone.

    Determines the machine's rounding behaviour and the error bounds. 

    static void exactinit (
    void
)

    Measured rather than assumed: the loop finds the actual epsilon of whatever the compiler and hardware do, so a target with extended-precision registers or a different rounding mode gets bounds that are true for IT. The error bound constants are Shewchuk's, derived for the 3x3 determinant.

    function expansion_sum_zeroelim¶

    Merges two expansions into their exact sum, dropping zero components. 

    static int expansion_sum_zeroelim (
    int elen,
    const double * e,
    int flen,
    const double * f,
    double * h
)

    Shewchuk's fast_expansion_sum: both inputs are ordered by increasing magnitude and non-overlapping, so the sum is a single merge pass with a running carry, no comparisons beyond picking the next-smallest component.

    "zeroelim" is what keeps the expansions short: an exact operation on two components usually produces a zero residue, and carrying it would lengthen every subsequent pass for no information.

    ── One deliberate departure from the published code ──────────────────────

    The original advances with enow = e[++eindex] and therefore reads e[elen] once, relying on the value never being used. That is a genuine out-of-bounds read harmless in practice, fatal under the AddressSanitizer this project's Debug build enables by default, and there is no reason to keep it. The merge below picks its next component only after testing the bound, which produces the identical sequence of arithmetic operations.

    Parameters:

    • elen Component count of e.
    • e First expansion, ordered by increasing magnitude.
    • flen Component count of f.
    • f Second expansion.
    • h Output expansion. Must hold elen + flen components.

    Returns:

    Number of components actually written to h.

    static double orient3dadapt (

    Warning:

    This is the macro a fused multiply-add would break.
