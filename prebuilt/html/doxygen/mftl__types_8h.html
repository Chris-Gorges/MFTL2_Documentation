Detailed Description

Core data structures of MFTL – the single place every struct is defined.

Author
Christian Gorges
Date
2026-08-14

Layer 1: types only, no behaviour, so module headers never include each other.

Layout: topology in AoS, geometry in SoA, one allocation per pool

  • Topology and identity -> Array of Structures. MFTL_Vertex (16 B), MFTL_Triangle (12 B), MFTL_HalfEdge (16 B). A remesher edits one entity at a time and touches most of its record when it does.
  • Geometry -> Structure of Arrays. Positions, normals, areas, centroids: kernels touch one component of every entity, every timestep.

Both live in ONE allocation per entity class, cut into cache-line-aligned sub-arrays (mftl_memory.h, src/object/object.c): 

MFTL_VertexPool   = one block -> rec[] pos[] normal[]
MFTL_TrianglePool = one block -> rec[] he[] area[] normal[] center[] verts[] neighbors[]

so a pool has exactly one capacity, and "the AoS grew but an SoA array did not" cannot be expressed.

Three invariants every module may assume

  1. Half-edges are triangle-indexed. Half-edge \(3t+k\) belongs to triangle \(t\) and \(\mathrm{next}(3t+k) = 3t+(k+1) \bmod 3\), so next, prev and face are arithmetic (mftl_topology.h), and the half-edge array lives inside the triangle pool at 3x its capacity. Anything that creates a triangle creates its half-edges at 3t, 3t+1, 3t+2.
  2. Ownership is a prefix. Entities [0, n_local) are owned by this rank, [n_local, n) are ghosts. There is no is_ghost flag; owner_proc only answers "whose is it" for a ghost.
  3. Positions live in verts.pos and only there. Spatial (Morton) ordering is applied to the pool itself (MFTLObjectReorderMorton()), never stored as a permutation, so there is one index space and one copy of each coordinate.

◆ MFTL_DERIVED_GEOMETRY

#define MFTL_DERIVED_GEOMETRY   0x2u

derived bit: tris.area/normal/center were computed over EVERY triangle, ghosts included, after the last change the library made to their inputs.

Set by MFTLComputeTriangleGeometry() over tris.n triangles. Cleared by any change of the entity set (MFTLObjectSetCounts() clears both bits), by the remeshing operators, by a redistribution's rebuild and by MFTLUpdateGhostPositions(); kept by MFTLObjectBuildDerived() and MFTLObjectReorderMorton(), which move no vertex. Moving owned vertices through verts.pos does NOT clear it: the library cannot see that. So a clear bit means "not current", and a set bit means "current unless the caller moved vertices since". MFTLRedistribute() recomputes the geometry of a body whose bit is clear before routing it.
