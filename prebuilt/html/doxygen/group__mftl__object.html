Detailed Description

Pool lifecycle, derived arrays, Morton ordering and the hot-loop iterators.

src/object/object.c is the only file allowed to write a pool pointer, a capacity or a block. Everything else changes size through MFTLObjectReserve(), MFTLObjectReserveAdditional() or MFTLObjectSetCounts().

Derived arrays and staleness

tris.verts and tris.neighbors are rebuildable caches, tracked by one bit; a second records whether the triangle geometry was computed since the library last changed its inputs:

Bit Arrays Invalidated by
MFTL_DERIVED_TOPOLOGY verts, neighbors any topology change
MFTL_DERIVED_GEOMETRY area, normal, center topology change, rebuild, ghost sync, remeshing operators; NOT vertex motion

Every MFTL_FOREACH_* iterator asserts on it in Debug. Vertex MOTION invalidates nothing: geometric consumers gather the authoritative positions and construct seam-corrected edges in registers, so there is no position-derived cache for a motion pass to leave stale.

Morton (Z-order) renumbering

MFTLObjectReorderMorton() sorts both pools along a space-filling curve. A position is quantised to 21 bits per axis and the bits are interleaved,

\[ Z(x,y,z) = \sum_{i=0}^{20} \Big( x_i\,2^{3i} + y_i\,2^{3i+1} + z_i\,2^{3i+2} \Big) \]

giving a 63-bit key that fits one uint64_t. The curve has the locality property that two points close in space have keys that agree in their high bits, so sorting by \(Z\) puts spatial neighbours near each other in memory. This is also the ordering an LBVH build consumes directly — see Bounding volume hierarchy and contact detection.
